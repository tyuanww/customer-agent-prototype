# 授权监控告警规则配置

本文件定义授权系统监控的告警规则和阈值。

---

## 一、告警阈值配置

### 1.1 授权成功率
```bash
THRESHOLD_AUTH_SUCCESS_RATE=95  # 低于 95% 触发告警
```

**说明：** 授权成功率 = 有效授权数 / 总主体数  
**正常范围：** >95%  
**告警级别：** P1 - 重要  
**响应时间：** 30 分钟

### 1.2 授权判断延迟
```bash
THRESHOLD_P99_LATENCY_MS=50  # 超过 50ms 触发告警
```

**说明：** P99 延迟 = 99% 的授权判断请求在此时间内完成  
**正常范围：** <50ms  
**告警级别：** P1 - 重要  
**响应时间：** 30 分钟

### 1.3 事实过期率
```bash
THRESHOLD_FACT_EXPIRY_RATE=5  # 超过 5% 触发告警
```

**说明：** 事实过期率 = 过期事实数 / 总事实数  
**正常范围：** <5%  
**告警级别：** P1 - 重要  
**响应时间：** 30 分钟

### 1.4 角色规则缺失率
```bash
THRESHOLD_POLICY_PENDING_RATE=1  # 超过 1% 触发告警
```

**说明：** policy-pending 率 = 缺少角色规则的主体数 / 总主体数  
**正常范围：** <1%  
**告警级别：** P2 - 警告  
**响应时间：** 工作时间内

### 1.5 数据库连接
```bash
# 数据库连接失败立即告警
```

**说明：** 监控脚本无法连接数据库  
**告警级别：** P0 - 严重  
**响应时间：** 5 分钟

## 三、告警规则详解

### 3.1 授权成功率告警

**触发条件：**
```sql
(有效授权数 / 总主体数) * 100 < THRESHOLD_AUTH_SUCCESS_RATE
```

**检查项：**
1. 有效授权数量是否正常
2. 授权是否被误撤销
3. 新主体是否自动签发授权

**常见原因：**
- 批量撤销授权
- 授权签发逻辑失败
- 来源或范围配置错误

**响应流程：**
1. 检查授权记录数量和状态
2. 检查最近的撤销操作
3. 验证授权签发逻辑
4. 如果需要，手动补充授权

### 3.2 授权判断延迟告警

**触发条件：**
```sql
AVG(authorization_deadline 执行时间) > THRESHOLD_P99_LATENCY_MS
```

**检查项：**
1. 授权记录数量是否激增
2. 索引是否健康
3. 数据库资源是否充足

**常见原因：**
- 授权记录数量过多
- 缺少必要的索引
- 数据库 CPU/内存/磁盘 I/O 瓶颈

**响应流程：**
1. 执行 EXPLAIN ANALYZE 分析执行计划
2. 检查索引使用情况
3. 检查数据库资源使用率
4. 如果需要，优化索引或清理过期数据

### 3.3 事实过期率告警

**触发条件：**
```sql
(过期事实数 / 总事实数) * 100 > THRESHOLD_FACT_EXPIRY_RATE
```

**检查项：**
1. 用户是否长时间未登录
2. 事实刷新逻辑是否正常
3. 登录流程是否有问题

**常见原因：**
- 用户长时间未登录（超过 24 小时）
- 飞书登录流程失败
- 事实创建逻辑失败

**响应流程：**
1. 检查过期事实的主体列表
2. 确认是否为预期行为（如测试账号）
3. 通知用户重新登录
4. 如果紧急，手动刷新事实

### 3.4 角色规则缺失告警

**触发条件：**
```sql
(缺少角色规则的主体数 / 总主体数) * 100 > THRESHOLD_POLICY_PENDING_RATE
```

**检查项：**
1. 新岗位是否缺少角色规则
2. 组织架构是否变更
3. 角色规则是否被误删除

**常见原因：**
- 新岗位上线，未配置角色规则
- 部门或岗位 ID 变更，旧规则失效
- 角色规则被误删除

**响应流程：**
1. 检查缺失的 (department_id, job_id) 组合
2. 确认是否为新岗位或组织变更
3. 联系管理员补充角色规则
4. 参考文档：docs/guides/grant-engineer-permissions.md

### 3.5 数据库连接失败告警

**触发条件：**
```bash
psql -c "SELECT 1" 失败
```

**检查项：**
1. 数据库进程是否运行
2. 网络是否通畅
3. 连接池是否耗尽
4. 权限是否正确

**常见原因：**
- 数据库进程崩溃或重启
- 网络故障或防火墙规则变更
- 连接池配置不合理
- 数据库用户密码变更

**响应流程：**
1. 检查数据库进程状态
2. 检查网络连通性
3. 检查连接池状态
4. 如果需要，重启数据库或调整连接池

## 四、告警抑制规则

### 4.1 时间窗口抑制

**规则：** 同一告警类型在 1 小时内只发送一次

**目的：** 避免告警风暴

**实现：**
```bash
# 在 /tmp 中记录最后告警时间
ALERT_FILE="/tmp/auth-alert-${ALERT_TYPE}.timestamp"
if [ -f "$ALERT_FILE" ]; then
    LAST_ALERT=$(cat "$ALERT_FILE")
    if [ $(($(date +%s) - LAST_ALERT)) -lt 3600 ]; then
        # 1 小时内，抑制告警
        exit 0
    fi
fi
echo "$(date +%s)" > "$ALERT_FILE"
```

### 4.2 维护窗口抑制

**规则：** 在计划维护窗口内，抑制非 P0 告警

**维护窗口：** 每周日 02:00-04:00（数据库维护）

**实现：**
```bash
# 检查是否在维护窗口内
if [ "$(date +%u)" = "7" ] && [ "$(date +%H)" -ge 2 ] && [ "$(date +%H)" -lt 4 ]; then
    # 在维护窗口内，只发送 P0 告警
    if [ "$ALERT_LEVEL" != "P0" ]; then
        exit 0
    fi
fi
```

### 4.3 测试环境抑制

**规则：** 测试环境的告警仅发送到日志，不发送到邮件/飞书

**实现：**
```bash
if [ "$DB_NAME" = "customer_agent_test" ]; then
    # 测试环境，只记录日志
    echo "[TEST] $ALERT_MESSAGE" >> /var/log/customer-agent/alerts-test.log
    exit 0
fi
```

## 五、告警升级策略

### 5.1 P0 告警（严重故障）

**初始响应：** 5 分钟内  
**升级时间：** 15 分钟未响应  
**升级对象：** on-call 团队 → 技术负责人 → CTO

**升级通知：**
```bash
# 15 分钟未确认，升级到 on-call 团队
send_urgent_alert "P0 告警未响应" "授权系统严重故障，15 分钟内无人响应"

# 30 分钟未解决，升级到技术负责人
send_urgent_alert "P0 告警未解决" "授权系统严重故障，30 分钟内未解决"
```

### 5.2 P1 告警（重要告警）

**初始响应：** 30 分钟内  
**升级时间：** 1 小时未响应  
**升级对象：** 运维团队 → 开发团队 → 技术负责人

**升级通知：**
```bash
# 1 小时未确认，升级到开发团队
send_email_alert "P1 告警未响应" "授权系统重要告警，1 小时内无人响应"
```

### 5.3 P2 告警（警告）

**初始响应：** 工作时间内  
**升级时间：** 24 小时未响应  
**升级对象：** 运维团队 → 开发团队

**升级通知：**
```bash
# 24 小时未确认，发送提醒
send_email_alert "P2 告警未响应" "授权系统警告，24 小时内无人响应"
```

## 六、告警确认和解决

### 6.1 告警确认流程

1. **收到告警通知**
   - 邮件或飞书群消息
   - 包含告警类型、级别、触发条件、当前指标

2. **确认告警**
   - 回复飞书群：`已确认：<告警类型>`
   - 或发送邮件到监控邮箱

3. **开始排查**
   - 参考快速响应手册：docs/runbook/authorization-incident-response.md
   - 执行诊断脚本：scripts/check-principal-facts.sh

4. **解决问题**
   - 根据故障类型执行解决方案
   - 验证问题已解决

5. **关闭告警**
   - 确认指标恢复正常
   - 在飞书群通报：`已解决：<告警类型>，原因：<根因>，措施：<解决方案>`

### 6.2 告警事后分析

**每次 P0/P1 告警后，进行事后分析：**
1. 根因分析（5 Why）
2. 影响范围和持续时间
3. 响应和解决时间
4. 改进措施（预防再次发生）
5. 文档更新

**事后分析报告模板：** docs/reports/incident-YYYYMMDD-<type>.md

## 七、告警规则调整

### 7.1 调整原则

**阈值调整：**
- 基于历史数据和实际业务需求
- 避免过度敏感（告警风暴）或过度钝化（漏报）
- 每月复核一次

**通知调整：**
- 根据团队反馈调整通知频率和渠道
- 避免打扰非工作时间（除 P0 告警）

**规则调整：**
- 基于事后分析的改进措施
- 新增规则前充分测试

### 7.2 调整流程

1. **提出调整需求**
   - 描述当前问题
   - 提出调整方案
   - 评估影响

2. **测试验证**
   - 在测试环境验证新规则
   - 确认不会漏报或误报

3. **应用到生产**
   - 更新监控脚本配置
   - 通知团队成员
   - 记录变更

4. **观察效果**
   - 观察 1-2 周
   - 收集团队反馈
   - 必要时进一步调整
