## 2. 权限线目标模型（A 组卡的共同依据）

- 一个真人一个主体。登录方式（飞书、账号密码）是这个主体的属性，不是两种主体。
- 飞书登录：按职务到角色的策略（`role_rules`）自动给最低权限（只读查询），不自动给发布、导入、授权。
- 账号密码登录：由主账号创建、重置、停用。
- 授权：主账号逐个人、逐店铺、逐动作授权；先预览再确认；撤销保留历史，不删行。
- 服务端判定唯一入口；前端只展示。无权限时前端显示原因和该找的角色。
- 本组卡不得改动授权判定语义；如发现必须改，停下报告。

## 3. A 组：权限与账号（最优先）

### A2b 坐席创建 definer 函数（替换 spawn 路径，路径 B）

- 背景：`docs/reviews/2026-10-24-seat-blocker-for-advisor.md`（`ddd960ea`）证实桌面端的坐席创建按钮调用本地 `spawn` 脚本，连接 `stack_owner`，在打包应用和生产环境里该脚本与目标数据库均不存在，按钮从未在生产成功过。生产 ACL 只有 `stack_owner` 能写 `backend_identity.subject_bindings` 与 `content_intake.role_rules`，四个能力角色全是 SELECT——这是有意设计，不是漏授权。顾问诊断（见对话记录）选定路径 B：`SECURITY DEFINER` 函数 + 最小输入，仿照已在生产跑通的 `backend_identity.admit_feishu_agent`（`0045_feishu_agent_admit.sql`）。
- 目标：新建迁移，加一个 definer 函数承担坐席创建，替换 `seat-account-ipc.ts` 里的 spawn 路径；API 改为调用该函数，不再连 `stack_owner` 的本地合成库。
- `admit_feishu_agent` 先例已满足、必须沿用的两条：
  1. **输入先做格式校验再使用**：`admit_feishu_agent` 对 `p_open_id` 用正则 `^ou_[A-Za-z0-9]{6,64}$` 校验，不合规直接 `RAISE EXCEPTION`。坐席创建函数对登录名、显示名同样先做格式校验（长度、字符集），不信任调用方传来的任意字符串。
  2. **函数本身只对一个数据库角色授权执行**：`REVOKE ALL ... FROM PUBLIC` 后 `GRANT EXECUTE ... TO <单一角色>`，不授权给 PUBLIC 或多个能力角色。坐席创建函数同样只授权给 API 实际使用的那一个角色，且该角色不应同时持有其他身份写权限。
- 坐席场景比飞书登录多一条、`admit_feishu_agent` 没有而必须补上的防碎裂坡：
  3. **岗位不能由调用方自由传入字符串**：`admit_feishu_agent` 把角色硬编码成 `'agent'`，坐席创建做不到硬编码（主账号要选"客服"或"客服主管"两种），但必须在函数内部用 `CHECK`/`IN (...)` 限定为这两个枚举值之一，并复用 `content_intake/role-ceiling.ts` 里已有的角色集合作为唯一真源，不能让调用方传任意字符串直接落库成角色。
- 不做：改变 `authorization_sources`/`authorization_deadline` 的判断逻辑；给能力角色新增对 `subject_bindings`/`role_rules` 的 GRANT；在应用层（API 代码）做角色校验后仍让 SQL 侧无条件信任。
- 验收：
  - 新迁移在真实 PG15 上跑通，`verifier.ts` 钉值同步更新。
  - 负向用例：非法登录名格式、非枚举岗位字符串、非 API 角色直接调用该函数，三者均被拒绝且不写入任何行。
  - 正向用例：API 创建坐席后，该账号能通过生产登录入口登录。
  - `seat-account-ipc.ts` 的 spawn 逻辑与对应脚本已删除或已确认不再被引用。
  - 报告中列出"函数内部角色枚举"与"`role-ceiling.ts` 角色集合"两者保持一致的核对方式（测试或构建期断言），防止后续新增角色时两处漂移。

#### A2b 补卡（2026-10-24，执行后新开）：调用权限缺口与登录名单缺口

执行方完成 A2b 后如实报告两处未满足原验收的缺口，顾问核实属实，判定**不放行部署**，两处一并改完才能上 0066/0067：

1. **调用权限缺口（新发现，比登录缺口更严重）**：`apps/api/src/content-intake/seats-http.ts` 的四条路由（`GET/POST /v1/intake/seats`、`POST /v1/intake/seats/:username/password`、`DELETE /v1/intake/seats/:username`）只调用 `actor(request)` 验证"已登录"，不验证"有权管理坐席"。`backend_identity.create_seat` 等函数只 `GRANT EXECUTE TO intake_business`——这是一个按能力分的数据库角色，不是按人分；只要 API 用这个角色连库，任何登录成功的会话（包括普通坐席）今天就能调用这四条路由创建坐席、停用他人、重置他人密码。这正是 A2b 原验收"函数内部角色枚举"条款背后要求的"调用者身份本身要可追溯、走现有授权链"，执行方自己在报告里记录了这一点却没有当成阻塞项。
   - 要求：四条路由在 `actor(request)` 之后，追加对调用者业务授权的检查，复用现有授权链（`authorization_sources` 或等价的 `grants` 判定），不新造一套判断。具体判给哪个角色/动作（例如要求 director/manager，或新增一个专门的 `seat-admin` 动作）由执行方按现有 `role_ceiling` 的角色集合提方案，不自行决定授权语义的新增项——如涉及新增动作枚举，先交回顾问确认。
   - 不做：绕过 `authorization_sources`/`authorization_deadline` 另写一套判断；把判断写死成"硬编码某个 user_id"。
   - 验收：负向用例——无坐席管理权限的已登录会话调用任一条路由，均被拒绝且不产生任何写入；正向用例——持有对应权限的会话可正常创建/重置/停用。

2. **登录名单缺口（执行方已发现并提出两个选项，顾问选定"要"）**：`scripts/synthetic-stack/identity-provider.ts` 的身份服务在固定名单 `SYNTHETIC_IDENTITIES` 之外，拒绝一切用户名，新建坐席因此无法登录，与 A2b 原验收"创建后能登录"矛盾。
   - 要求：身份服务在固定名单之外，额外接受"口令文件里有对应条目、且 `backend_identity.subject_bindings` 里存在对应 `synthetic_seat_<username>` 绑定并且 `enabled = true`"的账号登录。固定名单继续覆盖原有的合成身份，不删除、不替换，只是新增一条判定分支。
   - 不做：把坐席账号并入固定名单本身（那是静态配置，坐席是动态数据）；放宽固定名单之外任意用户名都能登录。
   - 验收：新建坐席创建后能从 `/password` 完成登录；停用后的坐席登录被拒；固定名单账号的登录行为不受影响（回归测试）。

两处改完后，按 A2b 原验收重跑一次完整正向流程（创建坐席 → 登录成功 → 该坐席按其岗位角色应有的权限能操作、不应有的被拒），再决定是否部署 0066/0067 到杭州。仍不 commit、不 push、不切杭州，直到顾问确认这版通过。

### D5 概览重做与质量闭环

- 目标：概览只显示真实聚合，没有接口写"未接入"；话术迭代接成闭环（不准反馈、无命中问题、待办、修订、效果对比）。
- 范围：先出设计文档，再实现；删除 `dashboard-manifest.ts` 中的固定样例数字，或隔离为仅本地预览可达。
- 依赖：C3、D4。
- 验收：生产路径不再出现任何固定样例数字，用测试证明。

## 7. E 组：检索与评测

### E1 检索评测集与评测脚本

- 目标：建立衡量检索好坏的尺子。
- 范围：300 到 500 条"顾客原话 → 应命中话术 id"；按类目与平台分层；必须包含"库里没有答案"的负例；开发集与测试集分开，测试集不参与调参；脚本输出 Top-3 命中率、MRR、无命中正确率。
- 数据：只用话术库本身的标题与问句改写出的合成问题，加话术师人工审核。不使用真实客户内容。
- 不做：任何模型训练。
- 验收：对当前 BM25 加向量加重排流水线跑出一份基线报告，可复现。

### E2 WeKnora 评估（调研卡）

- 目标：判断 WeKnora 能否承担检索，或只拆其模块借用。
- 说明：规划方没有读过 WeKnora 源码，仓库里也只有它与本项目同机运行的记录，此卡不预设结论。
- 范围：读 WeKnora 的检索、分块、重排模块；用 E1 的评测集对比；评估许可证、依赖、运维成本、与本项目授权模型的兼容性。
- 不做：把它接进生产链路。
- 验收：一页对比：能力、成本、风险、建议（直接用、借模块、不用），数字来自 E1 评测集。

### E3 小模型替换 MiniMax embo-01（依赖 E1）

- 目标：自托管向量与重排，替换外部 API。
- 候选：Qwen3-Embedding 0.6B 与对应重排小模型（来自公开榜单，需用 E1 实测，不以榜单为准）；在 4060 8G 与纯 CPU 两种环境下测延迟。
- 范围：先在离线脚本里比较，不改线上检索；保留 BM25 作为回退。
- 验收：评测报告含命中率、MRR、延迟、显存；明确是否优于 MiniMax。

### E4 服务端检索 RFC（依赖 E1、E2、E3）

- 目标：把检索从每台坐席电脑移到服务端。
- 范围：对比方案——PG 全文加 pgvector 加 RRF 加重排，与 WeKnora 借用方案；中文分词（PG 自带全文检索对中文分词弱，需分词扩展或沿用字符分词）；`pgvector` 需针对独立的 PG15 集群编译；索引随 release 更新的机制；权限过滤在检索前还是检索后。
- 不做：实现。
- 验收：方案含迁移成本、回退方式、评测对比；等用户确认后另开实现卡。

## 8. F 组：评审（只出方案，不改代码）

### F1 后端模型评审

- 内容：域枚举冻结与内容类型注册表；"发布要读权限、读权限要先发布"的死锁根因；授权判定收敛为单一入口（`authorization_sources` 与 `authorization_deadline` 合一）；六个授权概念能否收敛；事实租约由谁续期。
- 约束：A 组卡已在现有语义内完成权限线，F1 不阻塞 A 组。F1 的任何结论需要用户确认后才能开实现卡。

### F2 采集与脱敏策略评审

- 内容：L0 采集的告知与同意流程（现有 `pilot_recorded` 同意门）；姓名、地址、订单号、昵称的脱敏；保留期；店铺级开关与撤回；训练准入条件。
- 注意：与 2026-10-15 "不做采集"的决定相反，用户已于 2026-10-24 重新放开 L0；顾客聊天记录采集不在本期。
- 淘宝、抖音平台数据使用规则与个人信息保护法条款，规划方没有核实到可靠来源，需法务确认。
