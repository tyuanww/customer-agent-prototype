# 工程工作流程

> 状态：生效 · 仓库长期工作流程。
> 本文由 `AGENTS.md` 指定为流程真源，适用于功能开发、修复、诊断、文档、交付和发布。它规定如何执行，不授予新的 Git、真实运行或发布权限，不改变项目阶段门。

## 1. 规则归属与工作单元

| 内容 | 唯一维护位置 |
| --- | --- |
| 仓库纪律、权限和信任边界、设计原则、测试范围选择 | [AGENTS.md](../AGENTS.md) |
| 阶段顺序、Git / gstack 路由、证据复用与交接方法 | 本文 |
| 项目身份、仓间关系和生命周期 | [PROJECT_CHARTER.md](../PROJECT_CHARTER.md) |
| 模块所有权、专项验证命令和证据边界 | [架构参考](reference-project-architecture.md)、[验证指南](how-to-verify-desktop.md) |
| 任务目标、当前步骤、已有证据和待办决定 | 对应任务已有实施计划或执行清单 |
| 正式批准、阶段状态及不可变证据 | 治理仓的对应真源与受控证据位置，遵守[文档生命周期](reference-document-lifecycle.md) |

保留用户完整目标，以有依赖关系的可验收功能推进。功能是最小交付单元：一个明确行为及其必要的调用方、输出、失败处理、验证和说明。不能因为单个文件完成、PR 创建或 CI 通过，就把整个目标改写为已完成。

同一任务维护一份当前执行清单；已有计划可直接承载，不为每次“继续”新增计划或确认文档。不可变批准和实测证据分别保存，清单只引用。短任务可在当前对话说明范围与验收，不强制创建计划文件。

## 2. 固定阶段与退出条件

各阶段只在本次授权范围内执行；不适用阶段说明原因并跳过，缺少必要输入只阻塞依赖它的动作。

| 阶段 | 进入条件与工作 | 退出条件与交付物 |
| --- | --- | --- |
| 1. 范围与验收 | 识别只读或实施范围；核对当前实现、适用批准、工作区；明确结果、失败路径、验证面和负责人 | 目标与完成依据清楚；必需输入和授权已核对；缺项已提前提出。复杂方案比较边界后再实施 |
| 2. 实施 | 从明确基线建立独立工作区；完成一个功能闭环；先复现缺陷，再修复拥有该不变量的模块 | 实现、调用方、输出及说明一致；没有伪按钮、未接线状态或为通过测试而增加的特例 |
| 3. 验证 | 按 `AGENTS.md` 第 6 节运行相关检查；验证实际交付物及必要失败恢复 | 必需检查真实执行且通过；产物可被下游使用；证据绑定版本、输入和环境，未测范围明确 |
| 4. 审查 | 审查最终差异、设计边界、测试覆盖和文档一致性；复用内容未变的有效审查 | 阻断问题已修复并复核；风险和限制已披露；后续代码变更使受影响审查重新失效 |
| 5. PR 交付 | 在已有 commit / push / PR 授权内使用 `/ship`；检查最终暂存范围、PR 描述和 CI | 可审阅 PR 对应确切头提交；必需 CI 通过；需要新授权时材料完整可审阅。此时只称“PR 已就绪” |
| 6. 合并 | 明确合并授权覆盖该候选；复核当前头、基线、审查和检查，再执行 `/land-and-deploy` 的适用步骤 | 远端确认 MERGED，记录 merge SHA，核验该版本必需 CI；本地工作区有明确归属。合并不等于已部署 |
| 7. 环境验收与发布 | 按获批计划在指定环境安装、运行或部署；核对数据、身份、设备、负责人和回退条件 | 安装、运行、业务及发布验收分别有实际证据；交付位置、版本、限制和责任人明确。完成范围内全部承诺后才收尾 |

阶段 7 中测试环境部署、安装验收、灰度和正式发布的先后顺序由获批计划决定；不得通过固定流程把未批准环境或正式数据提前接入。功能修改回到阶段 2，证据变化回到受影响阶段，已完成且仍有效的其他步骤继续复用。

## 3. gstack 路由

gstack 是各阶段的执行工具。普通任务不遍历全部 Skill；第一次使用时读取实际安装的 Skill，适用步骤受用户范围、宿主规则和 `AGENTS.md` 约束。

| 任务 | 固定路由 |
| --- | --- |
| 功能开发 | 明确范围 → 实施 → 验证 → `/review` → 已授权的 `/ship` → PR CI；合并或发布获批后进入 `/land-and-deploy` |
| 中等以上架构 / 跨边界设计 | 实施前增加 `/plan-eng-review`；方案已批准且边界未变时复用，不重新走一轮方案批准 |
| Bug | `/investigate` 先取得复现和根因；只读请求止于诊断，修复请求继续实施、验证和交付路径 |
| 应用行为验证 | 仅报告用 `/qa-only`；测试并修复用 `/qa`。GUI、设备和业务验收按各自证据要求执行 |
| 文档 / 注释 / 规则 | 核对归属和一致性 → 编辑 → 差异与引用检查；Git 交付被授权时再进入 PR 流程，不默认启动运行时测试 |
| 产品 / 战略 / 设计方案 | 按实际问题选择 `/office-hours`、`/plan-ceo-review`、`/design-consultation` 或 `/plan-design-review` |
| 视觉检查 / 优化 | `/design-review`，按用户要求区分报告与修改 |
| 完整评审管线 | 用户要求时使用 `/autoplan`，不作为每个功能的默认前置步骤 |
| 独立代码评审 | `/review`，只读范围内不执行 auto-fix；不以审查发现自动扩大实施范围 |
| Spec / backlog | `/spec`；远端 issue 创建须在授权范围内 |
| 保存 / 恢复进度 | 需要交接时使用 `/context-save` / `/context-restore`，恢复后仅核对可能变化的证据 |
| 部署后核验 | 按已授权发布流程执行 `/land-and-deploy` 的环境核验；持续监控须有对应请求，可使用 `/canary` |

`/review` 和 `/ship` 不各自重复整套检查：交接版本、命令、结果及审查范围，由下一阶段判断证据是否仍有效。专项 Skill 明确要求的独立审查保留；子 Agent、多模型、外部服务遵守 `AGENTS.md` 第 8 节，不把并行审查固定为所有任务的前置条件。

Skill 缺失或工具失败时先判断能否完成等价核验：可选环节不阻塞主任务；必需环节不可替代时保留对应阻塞。不得声称未运行的 Skill、模型或设备已完成验证，不顺带升级、安装或修改全局 Skill。

## 4. Git 与授权处理

### 4.1 工作区和 PR

- 修改前确认仓库、分支、基线与 dirty 状态。已有任务使用自己的工作区；新功能从新鲜获取的目标基线建立独立 `codex/` 分支和 worktree，用户明确指定基线时遵从其要求。
- 一个功能对应一个可独立审阅、验收和回退的 PR。共用同一不变量的实现、消费者、测试和文档一起交付；不按文件数量限制拆 PR，也不把多个无关功能塞入一个 PR。
- 有依赖的 PR 明确标记顺序和基线；只有相互独立且授权允许的工作才并行。跨仓变更分别维护工作区、提交与 PR，用版本化合同或证据引用衔接。
- 每次暂存仅包含本功能的明确文件；存在 staging manifest 的候选按其校验。不能为获得干净工作树自动提交或丢弃内容。
- PR 描述围绕最终问题、行为、验证和限制编写；修订后检查描述和批准绑定是否仍适用。版本与生成物遵守已有唯一所有者，不因调用 Skill 新造版本源。
- 合并前确认用户批准的候选与实际 PR 头一致或符合批准中明确允许的变更范围；必需 CI 不得绕过。合并调用异常先回读远端状态，不能把客户端错误当作服务器未合并而重复操作。
- 合并后记录实际 merge SHA，并核验其检查；squash 不要求原 PR 头成为 main 的祖先。分支、worktree 和数据清理属于另行核对的动作，不由合并默认授权。

### 4.2 一次说清，持续有效

授权动作遵守 `AGENTS.md` 第 2 节。分别需要明确授权，不代表必须分多轮询问：用户可以在同一条指令中明确批准同一具体候选的多个动作；已覆盖动作直接执行。

在执行清单中引用授权来源，至少明确“对象 / 候选、动作、限制、有效期或次数（适用时）”。不为普通本地修改创建签字机制；正式批准继续使用其规定的受控记录，不在产品仓复制敏感原文。

请求批准前完成全部已授权且独立可做的准备，集中呈现结果、版本、检查、影响及本次待批准动作。已存在按候选哈希批准的规则仍按原规则执行，不能把“流程优化”当作未来未知候选的公开批准。

把“缺信息”和“缺授权”分开表达。负责人姓名、目标设备或环境等必要信息在阶段 1 提出，继续独立工作；“同意执行”不能填成负责人身份、验收意见或未说明的后续运行授权。对仅部分获答的问题，执行已明确部分，保留具体缺项。

## 5. 验证与证据复用

测试范围只由 `AGENTS.md` 第 6 节及适用专项计划决定，本文不维护第二份测试矩阵。

每项要复用的证据应能够回答：测了什么内容、用什么命令、在哪个环境和输入下运行、何时结束、结果是什么、原始结果在哪里。可记录在已有 PR、测试结果或执行清单中，不强制再造一套台账。

| 变化 | 处理 |
| --- | --- |
| 被测代码、构建输入、依赖、命令及相关环境 / 输入均未变化，证据未过期 | 复用本地验证与内容相同的审查，不因“继续”、切换阶段或调用另一个 Skill 重跑 |
| 实现、合同、依赖、生成物或受测范围发生变化 | 标记受影响证据失效，补充对应验证；影响不确定时按仓库规则扩大 |
| 仅说明文档变化，未改变验收合同、测试命令或构建输入 | 做差异、引用和一致性检查，复用不受影响的代码验证 |
| 真实输入、有效期、权限、环境或候选绑定变化 | 重新核对相关证据及授权，不能用内容相似或此前通过代替 |
| PR 头或合并版本变化 | 重新核对远端必需检查绑定；不能用另一个 SHA 的 CI 代替本次必需 CI |

对评测、导入、导出、报告和打包等交付链，首次受控运行前先用合成输入贯穿实际生产者与消费者，验证成功、允许的失败结果、完整字段、落盘 / 读取及必要清理；不可把单独通过的各段测试写成端到端通过。确有无法模拟的部分时明确缺口，由获批真实验证提供证据。

输出本身必须可验收：分母、逐项与汇总的一致性、失败原因、版本绑定、脱敏和读取方式均按对应合同验证。子进程退出 0 只证明进程结束，不能替代报告完整、包可安装或业务结论正确。

工具故障先区分观察失败与执行失败：已有进程或 CI 未结束时继续观察同一 handle；真实执行失败按其授权的重试范围处理。一次性运行、冻结题集、不可变证据和有效期不得自动重用、覆盖或延长。

## 6. 进度、等待与恢复

- 状态更新说明实际成果、证据、未解决问题和下一动作；避免把阅读规则、生成计划或等待用户本身写成产品交付。
- 对活跃进程和 CI 使用有界等待及适当退避，定期给出有意义更新。没有活跃 handle 的人工等待不称为“任务仍在运行”。
- 缺少决定时继续本目标内独立、已授权的工作；没有此类工作时报告具体阻塞。持续目标按宿主规定的连续阻塞阈值更新状态，不新增循环、轮询脚本或重复文档制造进展。
- 恢复执行只核对可能变化的分支、输入、批准和运行状态；接着做未完成步骤。已明确的授权、已通过且有效的验证和已完成成果继续保留。
- 发现计划偏离实际验收需要时，回到对应阶段修正当前执行清单。连续修补同一链路却没有形成可消费结果时，先检查完整合同和复现证据，再决定下一修改。
- 用户中途要求诊断、规则调整或状态说明时按新范围处理，保留原目标及授权；用户明确要求先处理某项时，先完成该项，不擅自执行被暂缓的动作。

## 7. 当前执行清单与完成声明

在已有任务计划中维护下列信息即可；短任务可在对话内表达，不要求照表制造文档。

| 必要信息 | 内容 |
| --- | --- |
| 完整目标与本次交付 | 用户最终目标、本次可验收功能及其依赖 |
| 完成依据 | 要观察到的行为 / 产物，验证方式和必要负责人 |
| 当前状态与证据 | 已完成项、版本、PR / CI / 实测证据引用及失效项 |
| 授权 | 已明确对象与动作；仍缺的授权或必要输入，分别列出 |
| 下一动作 | 可自主执行的下一步；若受阻，解除条件及独立工作是否已完成 |

完成声明按证据分开使用：“本地实现完成”“PR 就绪”“已合并”“安装验证通过”“业务验收通过”“已发布并验证”。后一个状态必须有自己的证据，不能由前一个状态推断。

提交最终结果前逐项核对用户目标和承诺；工具、文档、测试、PR 数量不能代替完成依据。交付包含安装或真实验收时，要给出可用产物及对应实际证据；仅有合成包或 hosted smoke 时如实注明。未完成项保留明确入口，不能缩小目标后宣布完成。

## 8. 流程维护

修改执行方法时更新本文；变更权限、安全或验证范围时在其所属真源中处理，并遵守用户授权。其他文件只链接本流程，不复制整套阶段表和 Skill 路由。不要把具体 PR、单次 run_id、临时阻塞或项目当前阶段写成本流程的永久规则。

流程调整按文档任务检查差异、引用、归属及一致性；如果改变了实际 CI、工具或运行代码，再按对应代码影响面验证。本文生效不构成自动提交、推送、合并、真实运行或发布授权。
