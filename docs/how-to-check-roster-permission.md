# 如何核对职位名单查询权

登录成功之后，看顶栏能不能查询。看到「没有权限，请找人开通。」只说明这次没有查询权。查询按钮还在，不表示服务端已经放行。

字段和状态见[职位名单权限模型](reference-job-roster-permission-model.md)。

本文按 0077 的现行路径核对。登录、目录刷新和候选登记都不签发业务 grant。权限页面保存或撤销的 grant 才是查询授权来源。0073 时期的自动 `query` 签发只保留为迁移历史。

## 前提

- API 以飞书登录启动，并且接上了业务库。没有业务库时，接口可以返回 `unknown`，那不是数据库放行。
- 空库第一次登记时，`ROSTER_TENANT_ID` 和 `ROSTER_APP_ID` 要成对设置。只设一个，或和库里已有的唯一一对对不上，登录投影会跳过。

## 步骤

1. 看桌面顶栏。出现那句固定句子时，`permission_state` 不是 `ready`。没有这句句子，并且状态是 `ready`，才表示当前店铺集里至少有一家店的查询截止时间还在。

2. 读 `GET /v1/auth/job`。两边都没有职务时返回 404，正文是「职务未识别」。有正文时只含 `title`、`directory`、`permission_state`、`message`、`actions` 五个字段。多出来的字段，桌面主进程会拒绝。

3. 按状态往下看，不要用按钮可见性代替这一步。

   - `pending`：正式职务已登记，当前事实仍有效，但没有匹配当前店铺集的查询 grant。未创建、已过期或已撤销的 grant 都不会出现在有效来源集合里。
   - `denied`：最低候选尚无业务 grant，或主体缺部门、职务编号对不上目录，或有业务库但没有读到库存状态。
   - `expired`：当前主体事实窗口已经过去。
   - `revoked`：当前主体事实未启用。
   - `ready`：`message` 为 `null`。当前店铺集里至少有一条有效查询授权。
   - `unknown`：没有业务库，接口无法从数据库证明查询资格。这个状态不是授权成功。

4. 发布、导入和授权不会因为这次登录自动出现。要开通查询，让有签发资格的账号在权限页面预览后保存。不要在登录路径补 `publish`、`import` 或 `grant`。

## 怎样确认

- `pending` 显示「查询权限或资料尚未就绪，请联系管理员核对。」，不推断一定缺发布。`denied`、`expired` 和 `revoked` 显示各自的拒绝提示。`ready` 和 `unknown` 的 `message` 为 `null`，但 `unknown` 不等于放行。
- 未知职务编号不会被当成标题。标题来自目录或本次登录快照。
- 人工 query grant 只能通过权限页面撤销。登录、目录刷新和候选 fallback 都不能重建它。

## 失败时

- 404「职务未识别」：数据库没有这个人的职务，本次登录快照里也没有。先确认飞书职务原文能对上目录，而不是改接口去猜一个标题。
- 投影被跳过：检查两个环境变量是否成对，以及库里是不是有多对 tenant/app。
- 自动 grant 退役和人工身份边界由 `0077_manual_identity_grants` 拥有；不要在旧 0047、0048、0049 已应用正文上原地修改。
